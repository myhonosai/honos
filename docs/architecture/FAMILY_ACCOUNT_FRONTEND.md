- `/staff/family-access`: explicit exact organization/school selection, the existing bounded `families` read, and a final current family-manager invitation read before revealing records. Choose an actual returned active family before inviting one email to PRIMARY_GUARDIAN, SECONDARY_GUARDIAN or VIEWER access. Ordinary revoke/end uses the selected family's returned PENDING/ACCEPTED invitation. Each action requires human confirmation. A historical receipt is not current access.
- The same route also has a separately labeled known-reference revoke/end form. Signed identity verification opens an empty form only: it proves no school permission, suspension state, family or invitation fact. A human supplies a previously known invitation UUID and exact school, selects revoke/end, and independently confirms that target. These untrusted selectors only enter the existing closed canonical command. The server reauthorizes the command and the browser strictly matches school, invitation and resulting status before a same-subject postcheck can reveal its historical receipt. This flow never lists families/invitations, invites, accepts, matches email to authority, or creates a new API.
- During suspension ordinary family/invitation records stay concealed on denial. The backend permits only authorized revoke/end. There is no suspension-time permission or invitation reader. After concealment or failed post-command verification, identity verification alone therefore cannot reveal a retained settlement: explicit replay of the original immutable command must obtain live backend authorization. UNKNOWN and later denial preserve its URL/body/key. No consequential retry occurs automatically.
- `/account/family-invitation`: normal signed-session gate, explicit current-identity verification, pasted invitation ID/code and deliberate confirmation. Email/subject/roles are never supplied by the acceptance body. Mixed staff/parent conflicts require school review and latch further acceptance retries, including after an earlier UNKNOWN result; unresolved evidence is retained until deliberate abandonment.
- Manual custody follows the owner-invitation model: share the fixed acceptance link and ID/private code separately through an approved secure channel. No code in URLs, fragments, logs, analytics or browser storage. HON sends no email or SMS.
- A closed organization/school query pair can prefill empty fields through the shared operational-navigation parser. It does not bind a scope or trigger a protected read, identity verification, command, family selection or invitation lookup. Extra, partial, duplicate and malformed selectors remain idle.

Privacy immediately hides/inerts private DOM on blur, visibility loss, pagehide, school change, session invalidation and unmount. Read revisions reject late results. Scope edits retire callbacks synchronously. An unsettled request remains owned by its original mounted controller, blocks replacement, and can reconcile only after explicit original-school and same-subject verification. A separate-tab sign-in link preserves mounted recovery. Discard is unavailable while active; deliberate abandonment warns that it cannot reverse or reconcile server effects. Full document destruction loses private recovery.

With ordinary records available, concealed known settlement may be revealed after a fresh authorized exact-school manager read and current identity check without another POST. In the known-reference flow the explicit exact backend replay is mandatory even when a validated response is privately retained. Retained callback revisions are retired before releasing the command lock.
