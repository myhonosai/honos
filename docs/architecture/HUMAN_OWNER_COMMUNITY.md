# Human HON owner community foundation

Migration `0081_human_owner_community.sql` adds **closed platform community discussions**, not a social publisher, marketplace or operational-data feed. The conventional authenticated `/community` workbench is equally available in Essential, Core and Complete. It uses the existing HON server session, `HonIdentityGuard`, explicit already-known school selection and same-origin human mutation guard. No public/anonymous page content or data endpoint exists.

## Eligibility and precise permission

A trusted database administrator must **manually verify the human's owner/operator capacity** in the private `hon.community_verifications` registry, recording the exact principal, organization, school, `OWNER`/`OPERATOR`, verification time and optional expiry. Revocation is an explicit `revoked_at`. The registry has no runtime/client/HQ function or UI for reading, creating or approving verifications. Do not seed actual people automatically; do not infer verification from an email domain, billing payer, display name, organization membership or role name. Administrative review procedures and evidence retention are operational prerequisites; this slice does not implement a review portal.

Every endpoint rechecks current active unique human identity, active organization/school, current active entitlement, exact-school unrevoked and unexpired staff-valid grants, role management-school scope and **`community.participate`**, plus current exact verification. A generic staff permission or OWNER role alone is insufficient. Community permissions are deliberately not assignable in the ordinary staff-role UI. Existing canonical OWNER roles receive permission definitions but **no automatic verification, consent or profile opt-in**. Operators require trusted explicit grants. Organization consent additionally requires verified `OWNER` capacity and exact **`community.organization.manage`**. Parent/family/HQ/system-role grants, organization-only grants, AI/automation/integration principals and delegated/Action Engine contexts are excluded. The existing staff eligibility predicate excludes HQ-granted identities; HQ cannot inherit member read even by mixing roles.

The selected school is an authority context, not a browsing directory or filter that grants access. The server resolves organization/principal from the verified subject and school; clients never submit actor, organization, permission or tier. Private roots retain ownership keys for integrity and authorization, but content output never exposes tenant, school, principal, user/contact or directory identifiers.

## Opt-in and visibility

- **Organization opt-in** is a versioned explicit verified-owner choice.
- **Member profile opt-in** is a separate versioned explicit human choice, with only a bounded display name. It is never copied from the personal identity directory and accepts no contact/avatar/URL/attachment fields.
- **Published** topics/posts/comments are intentionally shared across opted-in organizations with current verified members. This is a separate platform domain; no CRM, student, family, billing, membership, operational note or payment table is joined or returned.
- **Drafts, archives, private reasons and history** are visible only to their current author in that exact membership context. Other members cannot read unpublished historical versions, even after a discussion was published.
- An opt-out or membership/role/verification/entitlement revocation denies subsequent participation and hides that author's content from members. Withdrawing/archiving an ancestor hides descendants. An archived child is retained author-private only while its ancestor remains visible/published.
- `ARCHIVED` is terminal. Published content may be edited through a new published version or archived, never silently returned to draft. Archiving preserves the current title/body and records a reason. Kind/parent links cannot change. Topics → posts → comments is the only permitted tree; comments cannot nest.

No hard-delete endpoint exists. Full saved versions are immutable private storage; history UI returns at most 30 metadata summaries per page, never prior bodies or names. The current opted-in display name is used on read, not an old name snapshot. There is no directory or profile discovery endpoint.

## Inputs and outputs

Closed DTO/SQL contracts require exact keys and optimistic `expectedVersion`. Body ≤4,000 Unicode code points, title ≤120, private reason ≤300, display name ≤60. Explicit DRAFT creation is required. Controls, invisible/bidi characters, HTML markup, common URL/domain/contact syntax and attachments are rejected deterministically in API/contracts/SQL. This is a conservative **syntax restriction**, not automated moderation, classification or a guarantee that arbitrary plain text contains no sensitive information. Humans must never type personal, school-confidential or operational records; no operational import/lookup/attachment surface is provided. Bodies are rendered as escaped plain text, not Markdown/HTML or link previews. There are no URL fetches.

Closed output verification runs inside the API transaction and again in the browser. Unexpected keys (including operational, provider, contact, tenant or identity fields), invalid visibility/private reasons, cardinality and scope mismatches fail closed. SQL errors return fixed redacted messages, not content, internal errors, credentials or provider details. List/detail caches are private no-store; the page is dynamic and noindex. Access failures clear displayed content/settings/retry state. Changing school clears previous memory. No local storage and no automatic retries; uncertain saves retain exact inputs and a key in page memory for an explicit human retry.

## Storage and effect boundaries

All eight community tables use ENABLE + FORCE RLS, **no policies** and no runtime/browser/parent/staff/HQ row or column grants. Only five fixed SECURITY DEFINER entrypoints are executable by restricted `hon_runtime`; helpers/guards are denied. Functions use a pinned `pg_catalog,hon` search path and trusted migration owner. Live actor/permission/verification/topology rows are locked and rechecked before receipt replay. An advisory transaction lock serializes this small foundation's community versions/consent/receipts, not a persistent process. Read visibility evaluates current author membership and ancestor visibility. Reads are point-in-time authorization, not retroactive erasure of text already viewed/copied by humans.

Mutations atomically append versions, **redacted community-private audit events** and scoped fingerprinted retry receipts. Audit contains operation/entity/version/request/source, never text or personal contact. Receipts contain only content ID/version or a settings version, not body/name. No global school audit feed and **no outbox event** is emitted, so no provider/marketing/communication consumer can be accidentally activated. No Action Engine tool, scheduler, worker, moderation automation, AI/provider call, payment/invoice/membership mutation, external social publisher, campaign/notification, marketplace purchase/installation or anonymous consumer is registered.

## Deployment and validation

Apply migration `0081` as the trusted administrator, reconcile `infra/postgres/010_supabase_hon_runtime.sql`, then run canonical `011_verify_supabase_hon_runtime.sql` and `pnpm db:verify-rls`. Both verifiers track exact community tables, FORCE RLS/no-policy posture, trusted ownership, table/column ACLs, all helper/entrypoint ACLs/definer/search path and immutable/no-truncate trigger identity/type/enabled state. Drift is a blocker, not a fallback to broad grants.

`pnpm db:test-community` is guarded to exact disposable `localhost:5432/hon_community_validation` with `hon_community_owner` and `hon_community_runtime`; it refuses remote/configured databases. It tests identity/scope/permissions/verification/opt-in, author-private state/history, cross-school safe published sharing without operational projection, revocation and replay, optimistic versions/immutability, no side effects, rollback, ACL/RLS and deliberate verifier drift. Use `pnpm check`, `pnpm test`, `pnpm db:check`, `pnpm build` with database URLs unset for workspace validation. No remote migration, deployment, public publishing or provider activation is implied.
