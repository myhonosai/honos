# HON Core Platform Architecture
## PostgreSQL Tenancy, CRM & Billing Contracts, Transactional Outbox, and AI Action Engine

**Status:** Architecture specification — no product implementation has been started
**Scope:** The foundational design for tenant isolation, access enforcement, CRM and Billing service boundaries, public API contracts, reliable domain events, and controlled AI execution.
**Applies to:** HON School OS, Parent App / Eian, HON Complete employees, automations, integrations, and HON HQ support access.

---

## 1. Binding architecture decisions

| Decision | Standard |
|---|---|
| Tenant hierarchy | `Platform → Organization → School (subaccount) → operational records` |
| Tenant ownership | Every operational record is owned by exactly one `organization_id` and one `school_id`; a school must belong to that organization. |
| Data authority | PostgreSQL is the authoritative operational store. Redis, search indexes, analytics projections, AI context, and provider copies are derived state. |
| Isolation | Server-side authorization **and** PostgreSQL Row-Level Security (RLS) enforce scope. API clients never receive database credentials. |
| Cross-school behavior | There is no implicit global student record. A transfer/copy is an authorized, audited domain operation that preserves history. |
| Access model | Principal → organization membership → scoped role assignment → granular permission. This applies to human users, AI employees, automations, and integrations. |
| Business changes | Controllers, AI tools, webhooks, and automations submit typed commands to domain services. They never directly mutate business tables. |
| Reliability | A single database transaction performs business mutation, audit append, idempotency persistence, and event-outbox append. Publication occurs only after commit. |
| AI execution | AI may propose or execute only registered typed tools through the Action Engine. It never receives direct SQL, raw provider credentials, or an unrestricted internal API. |
| Authority modes | `AUTO`, `CONFIRM`, and `RESTRICTED` are resolved outside the model and enforced server-side for each action. |
| Financial safety | Membership terms are independent from payment schedules. Payment providers execute payments; HON owns policy, membership, pricing, state, and audit. Raw card data is never stored. |
| Support / HQ | HON HQ is a distinct control plane. Support access uses a scoped, expiring, reason-recorded impersonation session; it does not bypass RLS. |

> **Non-negotiable rule:** UI actions, API calls, automations, integrations, Eian, and all HON AI employees use the same domain service and business rules for the same action.

## 2. Terminology and identifiers

| Term | Meaning |
|---|---|
| **Organization** | Commercial customer account / owner group. It may operate one or more schools. |
| **School** | An independently operated location/subaccount, owned by one organization. It owns operational records. |
| **Principal** | An authenticated or service actor that may be authorized: human user, AI employee installation, automation, integration, or first-party service. |
| **Actor** | The principal that initiated a request. The actor is always recorded in audit and event metadata. |
| **Delegator** | The human principal whose authority caused a machine action to be allowed, when applicable. Delegation never enlarges a machine's own permission set. |
| **Permission** | A stable capability code such as `crm.lead.create`, `billing.membership.activate`, or `audit.read`. |
| **Role assignment** | A grant of a role to a principal at organization scope or at one explicit school. |
| **Tenant context** | The verified organization, permitted school set, principal, request ID, and correlation ID active for one database transaction. |
| **Domain service** | The sole application-layer entry point for business mutation and invariant enforcement. |
| **Action** | A potentially consequential typed command, especially one requested by an AI employee, Eian, automation, or an integration. |

### Identifier and time conventions

- Use UUID primary keys generated by PostgreSQL (`gen_random_uuid()`). IDs are opaque and never encode a tenant, user, or timestamp.
- Use `timestamptz` for every stored instant and UTC at rest. Store each school's IANA time zone for local scheduling/display.
- Use ISO-4217 `char(3)` currency codes and `numeric(19,4)` monetary amounts. Never use floating point for money.
- Use `created_at`, `updated_at`, `created_by_principal_id`, `updated_by_principal_id`, and an optimistic `version` on mutable business records.
- Archived operational records use `archived_at` / `archived_by_principal_id`; destructive deletion is exceptional and is separately audited.
- All primary entity tables have `id`, `organization_id`, and `school_id`; organization and school are **not** supplied by a browser request body.

## 3. PostgreSQL topology and security boundary

### 3.1 Database roles

```sql
-- Roles are examples; credentials are provisioned by deployment secret management.
CREATE ROLE hon_owner       NOLOGIN NOINHERIT;
CREATE ROLE hon_migrator    NOLOGIN NOINHERIT;
CREATE ROLE hon_api         NOLOGIN NOINHERIT NOSUPERUSER NOCREATEDB NOCREATEROLE NOREPLICATION;
CREATE ROLE hon_worker      NOLOGIN NOINHERIT NOSUPERUSER NOCREATEDB NOCREATEROLE NOREPLICATION;
CREATE ROLE hon_read_model  NOLOGIN NOINHERIT NOSUPERUSER NOCREATEDB NOCREATEROLE NOREPLICATION;

-- No application, browser, mobile client, AI provider, or integration receives
-- a role that owns tables or has BYPASSRLS.
ALTER ROLE hon_owner NOLOGIN;
ALTER ROLE hon_api NOBYPASSRLS;
ALTER ROLE hon_worker NOBYPASSRLS;
```

- Tables are owned by the non-login `hon_owner` role and use `FORCE ROW LEVEL SECURITY`.
- `hon_migrator` may perform schema migrations through a protected deployment path; it is not a runtime role.
- `hon_api` services interactive requests. `hon_worker` processes outbox, durable work, provider reconciliation, and scheduled automation using a real system principal and a verified tenant context.
- An application bug must not be able to issue arbitrary SQL from client input. RLS is defense in depth against accidental unscoped repository queries, not a substitute for domain authorization.

### 3.2 Schemas

```sql
CREATE EXTENSION IF NOT EXISTS pgcrypto;
CREATE EXTENSION IF NOT EXISTS citext;

CREATE SCHEMA tenancy;
CREATE SCHEMA iam;
CREATE SCHEMA people;
CREATE SCHEMA students;
CREATE SCHEMA crm;
CREATE SCHEMA billing;
CREATE SCHEMA audit;
CREATE SCHEMA eventing;
CREATE SCHEMA action_engine;
CREATE SCHEMA ai;
CREATE SCHEMA security;
```

Schemas are domain boundaries, not tenant boundaries. **No tenant gets its own schema or database.** Tenant isolation comes from explicit ownership columns, composite foreign keys, authorization, and RLS. This supports efficient migrations and operations at thousands of school locations without cross-tenant tables becoming ambiguous.

## 4. Exact multi-tenant foundation

### 4.1 Organization and school ownership

```sql
CREATE TABLE tenancy.organizations (
  id                         uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  legal_name                 text NOT NULL,
  display_name               text NOT NULL,
  slug                       citext NOT NULL UNIQUE,
  status                     text NOT NULL CHECK (status IN ('TRIAL', 'ACTIVE', 'SUSPENDED', 'CLOSED')),
  default_timezone           text NOT NULL DEFAULT 'America/Los_Angeles',
  created_at                 timestamptz NOT NULL DEFAULT now(),
  updated_at                 timestamptz NOT NULL DEFAULT now(),
  version                    integer NOT NULL DEFAULT 1 CHECK (version > 0)
);

CREATE TABLE tenancy.schools (
  id                         uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  organization_id            uuid NOT NULL REFERENCES tenancy.organizations(id) ON DELETE RESTRICT,
  code                       text NOT NULL,
  display_name               text NOT NULL,
  status                     text NOT NULL CHECK (status IN ('ONBOARDING', 'ACTIVE', 'SUSPENDED', 'CLOSED')),
  timezone                   text NOT NULL,
  currency                   char(3) NOT NULL DEFAULT 'USD',
  created_at                 timestamptz NOT NULL DEFAULT now(),
  updated_at                 timestamptz NOT NULL DEFAULT now(),
  version                    integer NOT NULL DEFAULT 1 CHECK (version > 0),
  UNIQUE (organization_id, code),
  UNIQUE (organization_id, id)
);

CREATE INDEX schools_by_organization_active
  ON tenancy.schools (organization_id, status, display_name)
  WHERE status IN ('ONBOARDING', 'ACTIVE');
```

The `UNIQUE (organization_id, id)` constraint intentionally supports composite foreign keys from every operational record. A row cannot claim an organization and school that do not belong together.

### 4.2 Principals, memberships, roles, and permissions

```sql
CREATE TABLE iam.principals (
  id                         uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  principal_type             iam.principal_type NOT NULL,
  display_name               text NOT NULL,
  status                     iam.membership_status NOT NULL DEFAULT 'ACTIVE',
  created_at                 timestamptz NOT NULL DEFAULT now(),
  disabled_at                timestamptz
);

CREATE TABLE iam.users (
  id                         uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  principal_id               uuid NOT NULL UNIQUE REFERENCES iam.principals(id) ON DELETE RESTRICT,
  external_identity_subject  text NOT NULL UNIQUE,
  email                      citext NOT NULL UNIQUE,
  given_name                 text,
  family_name                text,
  mfa_enrolled_at            timestamptz,
  created_at                 timestamptz NOT NULL DEFAULT now(),
  updated_at                 timestamptz NOT NULL DEFAULT now()
);

CREATE TABLE iam.organization_memberships (
  organization_id            uuid NOT NULL REFERENCES tenancy.organizations(id) ON DELETE RESTRICT,
  principal_id               uuid NOT NULL REFERENCES iam.principals(id) ON DELETE RESTRICT,
  status                     iam.membership_status NOT NULL DEFAULT 'INVITED',
  joined_at                  timestamptz,
  created_at                 timestamptz NOT NULL DEFAULT now(),
  updated_at                 timestamptz NOT NULL DEFAULT now(),
  PRIMARY KEY (organization_id, principal_id)
);

CREATE TABLE iam.permission_definitions (
  code                       text PRIMARY KEY,
  domain                     text NOT NULL,
  description                text NOT NULL,
  is_sensitive               boolean NOT NULL DEFAULT false,
  is_platform_managed        boolean NOT NULL DEFAULT true
);

CREATE TABLE iam.roles (
  id                         uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  organization_id            uuid NOT NULL REFERENCES tenancy.organizations(id) ON DELETE RESTRICT,
  code                       text NOT NULL,
  display_name               text NOT NULL,
  description                text,
  system_managed             boolean NOT NULL DEFAULT false,
  created_at                 timestamptz NOT NULL DEFAULT now(),
  updated_at                 timestamptz NOT NULL DEFAULT now(),
  UNIQUE (organization_id, code),
  UNIQUE (organization_id, id)
);

CREATE TABLE iam.role_permissions (
  role_id                    uuid NOT NULL REFERENCES iam.roles(id) ON DELETE CASCADE,
  permission_code            text NOT NULL REFERENCES iam.permission_definitions(code) ON DELETE RESTRICT,
  PRIMARY KEY (role_id, permission_code)
);

CREATE TABLE iam.role_assignments (
  id                         uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  organization_id            uuid NOT NULL,
  principal_id               uuid NOT NULL,
  role_id                    uuid NOT NULL,
  scope                      iam.assignment_scope NOT NULL,
  school_id                  uuid,
  starts_at                  timestamptz NOT NULL DEFAULT now(),
  ends_at                    timestamptz,
  granted_by_principal_id    uuid REFERENCES iam.principals(id) ON DELETE RESTRICT,
  revoked_at                 timestamptz,
  created_at                 timestamptz NOT NULL DEFAULT now(),
  CHECK (
    (scope = 'ORGANIZATION' AND school_id IS NULL)
    OR (scope = 'SCHOOL' AND school_id IS NOT NULL)
  ),
  CHECK (ends_at IS NULL OR ends_at > starts_at),
  FOREIGN KEY (organization_id, principal_id)
    REFERENCES iam.organization_memberships (organization_id, principal_id) ON DELETE RESTRICT,
  FOREIGN KEY (organization_id, role_id)
    REFERENCES iam.roles (organization_id, id) ON DELETE RESTRICT,
  FOREIGN KEY (organization_id, school_id)
    REFERENCES tenancy.schools (organization_id, id) ON DELETE RESTRICT
);

CREATE INDEX role_assignments_active_scope
  ON iam.role_assignments (organization_id, principal_id, school_id)
  WHERE revoked_at IS NULL;
CREATE INDEX role_permissions_permission ON iam.role_permissions (permission_code, role_id);
```

**Role model rules**

1. Seed platform-approved role templates into each organization (`owner`, `administrator`, `manager`, `instructor`, `front_desk`, `marketing`, `finance`) and permit custom roles there. This avoids an unsafe global role whose changes unexpectedly affect all customers.
2. A principal must have an active organization membership before it can receive a role at organization or school scope.
3. Organization-scoped role assignments apply to all current and future schools in the organization; school-scoped assignments apply only to their explicit school.
4. AI employees, integrations, and automations are principals with only the minimal role assignments and tool grants required. They are not superusers.
5. The UI may group permissions into role presets; the server authorizes the individual permission code.

### 4.3 People, families, students, and parent access

People are school-scoped because a school owns its operational relationship. A cross-school move or copy creates a new destination relationship under an audited transfer rather than quietly creating global shared records.

The Parent App/Eian uses `family_principal_access` plus family-specific policies, never broad staff roles, to reach a family and its children. A parent cannot acquire staff visibility by guessing IDs.

## 5. CRM canonical schema

CRM supports the lifecycle `Lead → Contact → Appointment → Trial → Enrollment → Membership` while keeping people, enrollment, billing, and scheduling as separate domains. The CRM domain owns pipeline state and sales activity; it does not directly own student, agreement, invoice, or payment tables.

```sql
CREATE TABLE crm.lead_sources (
  id                         uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  organization_id            uuid NOT NULL,
  school_id                  uuid NOT NULL,
  code                       text NOT NULL,
  display_name               text NOT NULL,
  source_class               text NOT NULL CHECK (source_class IN ('ORGANIC', 'REFERRAL', 'PAID', 'EVENT', 'PARTNER', 'MANUAL', 'OTHER')),
  is_active                  boolean NOT NULL DEFAULT true,
  created_at                 timestamptz NOT NULL DEFAULT now(),
  updated_at                 timestamptz NOT NULL DEFAULT now(),
  FOREIGN KEY (organization_id, school_id)
    REFERENCES tenancy.schools (organization_id, id) ON DELETE RESTRICT,
  UNIQUE (organization_id, school_id, code),
  UNIQUE (organization_id, school_id, id)
);

CREATE TABLE crm.pipelines (
  id                         uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  organization_id            uuid NOT NULL,
  school_id                  uuid NOT NULL,
  code                       text NOT NULL,
  display_name               text NOT NULL,
  is_default                 boolean NOT NULL DEFAULT false,
  is_active                  boolean NOT NULL DEFAULT true,
  created_at                 timestamptz NOT NULL DEFAULT now(),
  updated_at                 timestamptz NOT NULL DEFAULT now(),
  version                    integer NOT NULL DEFAULT 1 CHECK (version > 0),
  FOREIGN KEY (organization_id, school_id)
    REFERENCES tenancy.schools (organization_id, id) ON DELETE RESTRICT,

CREATE UNIQUE INDEX one_default_pipeline_per_school

  school_id                  uuid NOT NULL,
  pipeline_id                uuid NOT NULL,

  updated_at                 timestamptz NOT NULL DEFAULT now(),
  FOREIGN KEY (organization_id, school_id, pipeline_id)

  UNIQUE (organization_id, school_id, pipeline_id, position),

  UNIQUE (organization_id, school_id, id)
);

CREATE TABLE crm.leads (
  id                         uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  organization_id            uuid NOT NULL,
  school_id                  uuid NOT NULL,
  pipeline_id                uuid NOT NULL,
  pipeline_stage_id          uuid NOT NULL,
  primary_person_id          uuid NOT NULL,
  source_id                  uuid,
  owner_principal_id         uuid REFERENCES iam.principals(id) ON DELETE SET NULL,
  status                     crm.lead_status NOT NULL DEFAULT 'OPEN',
  program_interest_code      text,
  first_inquiry_at           timestamptz NOT NULL DEFAULT now(),
  next_follow_up_at          timestamptz,
  lost_reason_code           text,
  attribution                jsonb NOT NULL DEFAULT '{}'::jsonb,
  metadata                   jsonb NOT NULL DEFAULT '{}'::jsonb,
  won_at                     timestamptz,
  lost_at                    timestamptz,
  archived_at                timestamptz,

  CHECK ((status <> 'LOST') OR lost_at IS NOT NULL),
  CHECK (jsonb_typeof(attribution) = 'object'),

  FOREIGN KEY (organization_id, school_id, pipeline_id, pipeline_stage_id)
```

## 6. Billing canonical schema

### 6.1 Billing boundaries

- **HON owns:** membership terms, policy, price selection, payer/participant relationship, invoice state, payment schedule, ledger, customer experience, approval requirements, and audit.
- **Stripe/Square own:** card vaulting, payment instrument tokenization, network/payment execution, and processor-side transaction evidence.
- **No table stores:** PAN, CVV/CVC, magnetic stripe, raw bank-account credentials, or full provider authorization secrets.
- A payment is not presumed successful until it has been reconciled to the processor's terminal state. `UNKNOWN` is a real safety state.

**Financial immutability rule:** ledger entries, settled payments, and provider evidence are append-only. Corrections are compensating entries or formal reversals/refunds; they are never silent edits to history. The API role does not receive `UPDATE` or `DELETE` grants on immutable financial tables; stored service functions or a protected repository transaction append entries instead.

### 6.4 Required billing invariants enforced by domain services

Database constraints protect ownership, referential integrity, shapes, and arithmetic. Domain services additionally enforce:

1. An active agreement must have valid terms, eligible participants, and any required signature/policy conditions.
2. A billing account's payer is not the same concept as a membership participant; family memberships may have multiple participants and more than one payer.
3. A payment schedule cannot run past a non-renewed agreement end date without an authorized renewal/extension.
4. Invoice status and `amount_paid` are calculated from posted allocations and void/reversal facts, not independently edited UI fields.
5. A second charge attempt may not be initiated while a materially identical prior provider attempt is `PENDING`, `PROCESSING`, or `UNKNOWN`; it must reconcile first.
6. Provider webhooks are verified, deduplicated, mapped to a school-owned processor account, and processed idempotently.
7. Refunds, credits, discounts, waived charges, free months, extensions, and negotiated membership changes have explicit permission and Action Engine policies. They never arise from an AI inference alone.

|---|---|
| Identity provider | Authenticates human identity; MFA/session policy is enforced before reaching HON API. |
| API gateway | Verifies access token, request ID, rate limits, payload schema, and tenant path syntax. |
| Authorization service | Resolves principal, organization membership, accessible schools, permissions, feature entitlement, and parent/family relationship. |
| Domain service | Enforces the business-specific permission, state machine, policy, field-level constraints, and action authority. |
| PostgreSQL RLS | Enforces transaction-level tenant and school scope and table-operation permissions, preventing accidental cross-school query results. |
| Audit and outbox | Capture every consequential outcome in the same transaction. |

No one layer is treated as sufficient on its own.

### 7.2 Request context

For every interactive or worker transaction, the API creates one transaction and calls a database function after it has authenticated the principal. The requested schools must be a subset of the principal's actual active assignments.

```sql
CREATE OR REPLACE FUNCTION security.current_principal_id()
RETURNS uuid LANGUAGE sql STABLE AS $$
  SELECT NULLIF(current_setting('hon.principal_id', true), '')::uuid
$$;

CREATE OR REPLACE FUNCTION security.current_organization_id()
RETURNS uuid LANGUAGE sql STABLE AS $$
  SELECT NULLIF(current_setting('hon.organization_id', true), '')::uuid
$$;

CREATE OR REPLACE FUNCTION security.current_school_ids()
RETURNS uuid[] LANGUAGE sql STABLE AS $$
  SELECT COALESCE(NULLIF(current_setting('hon.school_ids', true), '')::uuid[], ARRAY[]::uuid[])
$$;

CREATE OR REPLACE FUNCTION iam.has_permission(
  p_principal_id uuid,
  p_organization_id uuid,
  p_school_id uuid,
  p_permission_code text
) RETURNS boolean
LANGUAGE sql STABLE SECURITY DEFINER
SET search_path = iam, pg_temp
AS $$
  SELECT EXISTS (
    SELECT 1
    FROM iam.organization_memberships om
    JOIN iam.role_assignments ra
      ON ra.organization_id = om.organization_id
     AND ra.principal_id = om.principal_id
     AND ra.revoked_at IS NULL
     AND ra.starts_at <= now()
     AND (ra.ends_at IS NULL OR ra.ends_at > now())
     AND (ra.scope = 'ORGANIZATION' OR ra.school_id = p_school_id)
    JOIN iam.role_permissions rp ON rp.role_id = ra.role_id
    WHERE om.organization_id = p_organization_id
      AND om.principal_id = p_principal_id
      AND om.status = 'ACTIVE'
      AND rp.permission_code = p_permission_code
  )
$$;

CREATE OR REPLACE FUNCTION security.tenant_scope_permits(
  p_organization_id uuid,
  p_school_id uuid
) RETURNS boolean
LANGUAGE sql STABLE SECURITY DEFINER
SET search_path = security, iam, pg_temp
AS $$
  SELECT
    p_organization_id = security.current_organization_id()
    AND p_school_id = ANY(security.current_school_ids())
    AND EXISTS (
      SELECT 1
      FROM iam.organization_memberships om
      WHERE om.organization_id = p_organization_id
        AND om.principal_id = security.current_principal_id()
        AND om.status = 'ACTIVE'
    )
$$;
```

A protected `security.set_request_context(principal, organization, school_ids, request_id, correlation_id)` function must verify the caller's active organization membership and scoped role assignments before calling `set_config(..., true)`. The database credentials are held only by HON backend services; clients cannot invoke arbitrary SQL or set GUCs. The function also records the request/correlation ID used by audit and events.

The API sets context only with `SET LOCAL` semantics inside a transaction. It must reset/close a pooled connection at transaction completion. Never rely on connection-wide tenant settings.

### 7.3 Example RLS policy: CRM leads

```sql
ALTER TABLE crm.leads ENABLE ROW LEVEL SECURITY;
ALTER TABLE crm.leads FORCE ROW LEVEL SECURITY;

CREATE POLICY crm_leads_select ON crm.leads
  FOR SELECT
  USING (
    security.tenant_scope_permits(organization_id, school_id)
    AND iam.has_permission(
      security.current_principal_id(), organization_id, school_id, 'crm.lead.read'
    )
  );

CREATE POLICY crm_leads_insert ON crm.leads
  FOR INSERT
  WITH CHECK (
    security.tenant_scope_permits(organization_id, school_id)
    AND iam.has_permission(
      security.current_principal_id(), organization_id, school_id, 'crm.lead.create'
    )
  );

CREATE POLICY crm_leads_update ON crm.leads
  FOR UPDATE
  USING (
    security.tenant_scope_permits(organization_id, school_id)
    AND iam.has_permission(
      security.current_principal_id(), organization_id, school_id, 'crm.lead.update'
    )
  )
  WITH CHECK (
    security.tenant_scope_permits(organization_id, school_id)
    AND iam.has_permission(
      security.current_principal_id(), organization_id, school_id, 'crm.lead.update'
    )
  );

CREATE POLICY crm_leads_no_delete ON crm.leads
  FOR DELETE USING (false);
```

Apply an equivalent operation-specific policy to every tenant-owned table. For example, invoices use `billing.invoice.read` / `billing.invoice.create` / `billing.invoice.update`; immutable ledger rows receive only `SELECT` and controlled `INSERT` policies, with no update/delete policy.

### 7.4 Parent and Eian policy pattern

Staff/table permissions must not accidentally allow family users to query the whole school. For a parent-visible table, define a dedicated policy that joins the row through `family_principal_access`, such as the family linked to a student or billing account. Eian acts as a family-scoped principal and receives only parent-safe tool grants. It cannot pass arbitrary `student_id`, `family_id`, or school identifiers through to a domain service.

### 7.5 Cross-school transfer / copy pattern

A transfer service requires explicit source and destination scope, permissions for both locations, a tenant-wide policy check, and a transaction/audit trail:

1. Validate the organization owns both schools and the actor has `student.transfer.outbound` at source plus `student.transfer.inbound` at destination.
2. Lock source record(s), copy or move permitted current operational relationships, and retain source history.
3. Create `students.student_transfers` with source/destination, mode (`COPY` or `MOVE`), reason, actor, linkage map, and result.
4. Emit `student.transfer.completed.v1` only after commit.
5. Never make an accidental update of `school_id` the transfer mechanism.

## 8. Core domain-service pattern

### 8.1 Command path

```text
HTTP / Mobile UI / AI Tool / Automation / Provider Webhook
    → request authentication and schema validation
    → authorization context resolution
    → Action Engine (when consequential / AI-triggered)
    → typed domain command
    → domain service transaction
        → load and lock aggregates
        → enforce permission, state, policy, and invariants
        → mutate authoritative tables
        → append audit event
        → persist idempotency result
        → append outbox events
    → commit
    → response
    → asynchronous outbox publication and projections
```

### 8.2 Standard command context

Every mutating domain service accepts a server-created context, never client-supplied actor or tenant fields:

```ts
type CommandContext = {
  principalId: string;
  principalType: 'HUMAN_USER' | 'AI_EMPLOYEE' | 'AUTOMATION' | 'INTEGRATION' | 'SYSTEM_SERVICE';
  organizationId: string;
  allowedSchoolIds: string[];
  schoolId: string;
  requestId: string;
  correlationId: string;
  causationId?: string;
  idempotencyKey: string;
  source: 'HUMAN_UI' | 'PUBLIC_API' | 'AI' | 'AUTOMATION' | 'INTEGRATION' | 'MIGRATION';
  delegatedByPrincipalId?: string;
  actionRequestId?: string;
};
```

A domain service must not infer tenant scope from an entity ID. It receives the scope explicitly from verified context, then queries using both `organization_id` and `school_id`.

### 8.3 Standard mutation algorithm

1. **Validate input shape** with a typed command schema before beginning the transaction.
2. **Set verified database request context** for this transaction.
3. **Replay protection:** claim/create the idempotency record keyed by `(principal_id, route_or_action_code, idempotency_key)`. If a completed result exists, return it verbatim; if in progress, return the operation status rather than duplicate work.
4. **Authorize:** check the exact permission and school scope inside the service, even though RLS protects row access.
5. **Load aggregate(s)** by `(organization_id, school_id, id)` using `FOR UPDATE` where a state transition or financial concurrency requires it.
6. **Apply invariant and state-transition checks.** Use explicit transition maps, not generic patching of status fields.
7. **Persist the authoritative change** with optimistic version checks for normal concurrent updates.
8. **Append an audit record** with source, actor, optional delegator, before/after redacted change set, action result, and correlation.
9. **Append domain event(s)** to the transactional outbox in the same commit.
10. **Store idempotency outcome** and commit.
11. **Return a resource representation and version/ETag.** Do not wait for unrelated async projections or notifications to claim success.

### 8.4 Service responsibilities and anti-patterns

| Component | May do | Must not do |
|---|---|---|
| Controller / resolver | Authenticate, parse route, validate request DTO, map response/problem details | Contain business state transitions or direct repository mutation |
| Query service | Tenant-scoped read models, filters, pagination, field shaping | Mutate records or use unscoped analytics tables for operational decisions |
| Domain service | Own invariants, atomic mutation, audit/outbox append, concurrency | Send email/SMS, call AI, or synchronously invoke external provider after database mutation |
| Provider adapter | Translate HON command to provider API; validate webhooks; reconcile state | Decide HON membership policy or make a provider model the source of truth |
| Event handler | Build projections, enqueue work, initiate independently idempotent follow-up | Assume exactly-once delivery or perform uncontrolled inline cascading writes |
| AI tool adapter | Strictly parse a registered action schema and submit action request | Query arbitrary tables, compose SQL, or invoke privileged provider credentials |

### 12.4 Publisher and consumer algorithm

1. The domain transaction inserts the event as `PENDING`; it does **not** publish to a broker before commit.
2. A worker claims a bounded batch with `FOR UPDATE SKIP LOCKED`, sets a lease (`claimed_until`), then publishes to the broker/event transport.
3. The worker marks successfully acknowledged events `PUBLISHED`. If it crashes after publishing but before marking published, it may publish again.
4. Consumers are therefore **at-least-once** and must be idempotent. They insert `(consumer_name, event_id)` in `consumer_receipts` inside their own transaction before or with their side effect.
5. Retryable failures use exponential backoff via `available_at`; a bounded failure count moves an event to `DEAD_LETTER` and creates a visible operational work item.
6. Ordering is only guaranteed where explicitly designed—for example, an aggregate-specific sequence/locking strategy. Consumers must remain correct under cross-aggregate reordering.

### 12.5 Outbox rules

- Never make a feature depend on a synchronous event handler for correctness of the original command result.
- Never use a generic “database changed” event; use a stable named business fact and version it when evolving payload contracts.
- Never put full PII, raw payment provider payloads, or secrets into broadly consumed events.
- Event processing is tenant-scoped. A consumer cannot load an aggregate without carrying the envelope's organization and school context.

## 13. Action Engine: controlled AI and consequential work

### 13.1 Purpose

The Action Engine is the mandatory policy and execution gateway between an AI model's structured tool request and an authoritative HON domain service. It also supports automation, integrations, and human maker-checker workflows where desired.

```text
AI conversation / workflow
  → registered typed HON tool
  → Action Engine preflight
      → tenant scope
      → tier entitlement
      → tool allowlist
      → principal permission
      → resource/policy validation
      → authority mode resolution
      → approval rule
  → approved typed domain command
  → domain service
  → verify outcome
  → audit + outbox + durable work update
```

An LLM can suggest the command parameters. It cannot grant itself a tool, permission, tenant scope, approval, policy exception, or authority mode.

### 13.4 Authority resolution

Authority modes are ordered by restrictiveness:

```text
AUTO < CONFIRM < RESTRICTED
```

The effective authority mode is the most restrictive applicable value:

```text
max_restrictiveness(
  action_catalog.platform_authority_floor,
  organization policy if later introduced,
  school_action_policy.authority_mode,
  agent_tool_grant.configured_authority_mode,
  risk escalation for amount/recipients/data sensitivity/provider health
)
```

A school can choose a more restrictive setting for an action. It cannot make an action less restrictive than the platform safety floor, its tier/permission constraints, or an applicable organization policy. A personalized agent name, avatar, voice, personality, or AI Customizer surface never changes this calculation.

### 13.5 Execution semantics by authority mode

| Effective mode | What an AI tool request does | What is required before execution |
|---|---|---|
| **AUTO** | Creates an action request, completes preflight, then starts execution without waiting for a human. | Active tenant context, tier entitlement, enabled registered tool, active agent installation, exact permission, all domain/policy checks, valid typed input, no hard approval condition, and idempotency key. |
| **CONFIRM** | Creates a complete executable proposal and transitions to `AWAITING_APPROVAL`. It does not call the domain service that performs side effects. | An authorized human sees the exact reviewed action, target, amount/recipients/material changes, policy reasoning, and expiry. Approval input hash must equal current request input. |
| **RESTRICTED** | Denies side-effect execution with `ACTION_RESTRICTED`. AI may provide analysis or create a non-executable recommendation/task, but cannot create a queued executable command. | A human uses the conventional protected UI/API with the appropriate permission and any human approval workflow. |

A `CONFIRM` request is revalidated after approval and immediately before execution. If the record version, availability, price, schedule, policy, permissions, or payment status is stale, the action returns to review/denial rather than executing old intent.

### 13.6 Action preflight and state machine

```text
RECEIVED
  → VALIDATING
      → DENIED                  (scope, entitlement, tool, permission, policy, or schema failure)
      → AWAITING_APPROVAL       (effective mode CONFIRM)
      → APPROVED                (AUTO preflight passed or human approval granted)
  → EXECUTING
      → SUCCEEDED               (domain result verified)
      → FAILED                  (known terminal error)
      → UNKNOWN                 (external outcome cannot safely be determined)

AWAITING_APPROVAL
  → APPROVED | DENIED | EXPIRED | CANCELLED
APPROVED
  → EXECUTING | EXPIRED | DENIED
```

The preflight snapshot persists:

- resolved organization and school;
- action code/schema version/tool grant;
- tier and permission decision;
- effective authority and every policy source used;
- resource IDs and optimistic versions;
- material change summary / exact parameters;
- recipient count and financial amount where relevant;
- required reviewer criteria and approval expiry;
- model/tool-run reference for audit, **not** hidden model reasoning.

### 13.7 Approval design

Approval is a security decision, not a chat acknowledgement.

1. The approval inbox displays an exact human-readable preview and the normalized payload being approved.
2. The reviewer must have the action's configured approval permission; a requester cannot approve their own request when two-person review is required.
3. Approval is bound to `approved_input_hash`, school, action code, and policy version; edits create a new review cycle.
4. Approval expires. A future time-sensitive message, class booking, price, refund, or campaign is revalidated before execution.
5. Approval, rejection, expiration, and execution outcome create audit records and outbox events.
6. An AI cannot silently substitute recipients, amount, content, provider account, schedule, or target after approval.

### 13.8 Tool Gateway contract

Each agent-visible tool has a server-owned JSON Schema and maps to one action catalog code. Example:

```json
{
  "name": "schedule_trial",
  "actionCode": "crm.trial.schedule",
  "inputSchema": {
    "type": "object",
    "additionalProperties": false,
    "required": ["leadId", "classOccurrenceId", "attendeePersonIds"],
    "properties": {
      "leadId": { "type": "string", "format": "uuid" },
      "classOccurrenceId": { "type": "string", "format": "uuid" },
      "attendeePersonIds": {
        "type": "array",
        "minItems": 1,
        "items": { "type": "string", "format": "uuid" }
      },
      "notes": { "type": "string", "maxLength": 1000 }
    }
  }
}
```

The gateway checks strict schema, tenant-resolves every referenced ID, creates the `action_requests` record, and passes a typed command into `TrialService` only after Action Engine resolution. An LLM never calls internal REST endpoints directly.

### 13.9 AI Customizer boundary

The AI Customizer may let a Complete school enable/disable or configure **approved, centrally registered** tools and workflows for that school's agents. It cannot:

- invent tool code that reaches arbitrary internal APIs;
- assign a permission the agent principal lacks;
- lower the platform authority floor;
- alter tenant isolation, financial processing, payment access, audit, or approval implementation;
- export another school’s private data into a shared asset.

Configuration is stored per school in `ai.agent_tool_grants` and policy tables. Shared customizer/marketplace assets are signed, versioned logic/configuration templates; installation maps them to the receiving school’s own records, roles, consent, tier entitlement, and action policy. Product-level learning uses only explicitly approved, privacy-preserving aggregated telemetry; tenant operational data remains isolated.

| Initiator | Entry mechanism | Required controls | Domain execution |
|---|---|---|---|
| Staff web UI | Versioned API command | user permission, field/state policy, idempotency | same service |
| Parent App / Eian | Family-scoped API/tool | family access, parent-safe tool, Eian policy/approval | same service |

| Integration webhook | verified adapter command | signature, provider mapping, external-event dedupe, tenant match | same service |
| HON HQ support | scoped impersonated API command | support reason, expiry, elevated permission, audit | same service |

This is how HON prevents duplicate state machines while preserving different UX paths.

## 15. Operational failure and recovery behavior

### Payments

- The payment adapter sends a provider idempotency key derived from `billing.payment_attempts.id`.
- A timeout leaves the attempt `UNKNOWN` until reconciliation resolves the actual provider outcome.
- Retrying the original action reconciles the existing attempt first; it does not create a second charge.
- Provider webhooks are authenticated, deduplicated, stored in a protected raw-evidence store when needed, and transformed into an internal command.

### Communications and automation

- Outbound communication has its own message/delivery lifecycle; provider acceptance is not delivery.
- Automation executions persist trigger, entity, intended action, attempts, outcome, and correlation IDs.
- A retry may execute only after checking consumer/action idempotency state.

### AI and voice

- Voice is an interface. If it fails, the same conversation ID, active agent, work item, permission model, approvals, and text pathway remain available.
- An AI provider failure transitions to approved fallback or reduced AI mode. It cannot relax Action Engine rules or take on a fallback model with greater authority.
- The conventional CRM and Billing interfaces remain operational during all AI degradation.

## 16. Required test matrix before relying on these foundations

| Area | Required verification |
|---|---|
| Tenant isolation | Attempts to fetch/update/delete a record by another school UUID fail under API and direct RLS query paths. |
| Composite integrity | Inserting a record with Organization A + School B fails at the foreign key. |
| Role scope | Organization role works across allowed schools; school role fails outside its explicit school. Revoked/expired grants immediately deny. |
| Parent access | Parent/Eian can access only linked family/student/billing-safe data; cannot enumerate other people or school reporting. |
| RLS pooling | A reused database connection cannot inherit the preceding request’s school IDs or principal. |
| CRM lifecycle | Create → activity → task → trial → attendance → conversion preserves attribution and audit/outbox lineage. |
| Billing lifecycle | Draft → signature/activation → schedule → invoice → payment attempt → webhook reconciliation → allocation/ledger is consistent and idempotent. |
| Payment unknown | Simulated provider timeout produces `UNKNOWN`, reconciliation finds original transaction, and retry does not double-charge. |
| Event outbox | Transaction rollback publishes no event; publish-after-crash redelivery is harmless to idempotent consumers. |
| Authority Auto | Authorized agent executes only a registered permitted low-risk action and logs tool/action/audit chain. |
| Authority Confirm | No side effect occurs before approval; changed payload/version after approval forces re-review. |
| Authority Restricted | AI tool cannot enqueue or execute a restricted financial/publication/purchasing action. |
| Approval separation | A requester cannot satisfy a two-person approval rule; expired/revoked approvals cannot execute. |
| Tier entitlement | Essential/Core cannot access Complete employee/action capabilities despite a forged client request. |
| Provider failure | Degraded provider isolates only dependent action; CRM/Billing UI state remains understandable and operational where possible. |

## 17. Implementation sequence

1. Provision PostgreSQL roles, schemas, migration tooling, audit/outbox primitives, request-context functions, and RLS test harness.
2. Implement tenancy, principals, organization memberships, role/permission engine, tier entitlement service, and HQ-support scoped impersonation design.
3. Implement people/family/student foundation plus staff and parent/Eian authorization paths.
4. Implement CRM tables, services, endpoints, events, tests, and conventional UI contracts.
5. Implement billing catalog/accounts/agreements/schedules/invoices/ledger before attaching Stripe and Square adapters.
6. Implement signed webhook ingest and reconciliation, then payment initiation with idempotency/unknown-outcome handling.
7. Implement Action Engine, approval inbox, agent installations/tool grants, and audit/event integration.
8. Add deterministic automation and AI tools only after the underlying conventional services are verified.
9. Add read models, reporting, notifications, scheduling integration, migration tooling, observability, and provider-health/circuit-breaker operations iteratively.

> **Definition of completion for each command:** business invariant, permission check, RLS policy, API contract, audit record, outbox event, idempotency behavior, failure behavior, test coverage, and documentation all exist together. A screen or a working demo alone is not a completed HON capability.

## 18. Explicit next design dependencies

This specification establishes the foundation. Before coding CRM-to-Billing conversion and live payment/automation flows, the next architecture documents should define:

1. **Scheduling domain contract** — class occurrence, enrollment/booking, eligibility, capacity, attendance, makeups, and trial integration.
2. **Tier entitlement schema** — plan, subscription, add-ons, grants, feature checks, and credit allowance ledger.
3. **Communication domain** — consent, templates, messages, channels, delivery webhooks, recipient policies, and opt-out enforcement.
4. **Durable Work Engine** — Work Item schema, retries, waits, approvals, dependency graph, AI team orchestration, and realtime work state.
5. **Provider adapter contracts** — Stripe/Square/Twilio abstractions, secrets boundary, webhook verification, health/circuit breaker semantics, and reconciliation ownership.
6. **PII and retention policy** — field-level encryption/search approach, data retention/export/deletion rules, minor/family safeguards, and regional compliance decisions.

These dependencies do not alter the core rule: every later domain must carry the same tenant ownership fields, use scoped commands, emit transactional domain events, honor Action Engine policy when machine-initiated, and retain conventional UI/API operation independent of AI availability.
