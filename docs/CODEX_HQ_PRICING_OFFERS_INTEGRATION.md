## Owner workflow

Open **HON HQ → Pricing & Offers**. Existing signed-session HQ layout and independently authorized HQ shell remain. The workbench then independently verifies identity, current HQ role and the protected SaaS offer-management read. Operators with the required billing permission can read; only currently authorized owners can issue commands. All APIs and protected database functions retain independent checks.

1. Overview loads current published configuration, backend drafts, six payment kinds and server-listed sales state. One product, HON OS. No configured price, quantity or AI-credit default is invented.
2. Open a version, start a local new set or explicitly copy a saved version. Published, retired and discarded terms are read-only. Copying never changes the original version.
3. Edit the **whole set**, including every offer returned (up to 12, including multiple offers of one kind). The UI never truncates it to six rows. Select any of the six kinds when adding an offer. Amounts are exact USD dollars/cents converted to integer minor units; all other commercial policies use the exact closed 0181 enums. Server-owned offer IDs, statuses, intervals and authority are never submitted.
4. Save Complete Draft sends create or full-replacement revise with the expected revision. Terms references and set-level founder pool limit apply to the complete set. Per-offer eligibility, sale limit, price lock/months, annual renewal, refund window, cancellation timing, UTC sale windows and planned AI credits/fair-use reference use the merged contract. Missing draft terms can remain incomplete where allowed; the server determines publication readiness.
5. Review a **saved** draft. No local price or quote is used as publication authority. The saved-set read supplies quotes, annual savings, monthly equivalents, break-even, founder comparisons, issues and digest. Review shows all offer terms. Changed revisions/digests require reload and a fresh review. Edits and concealment invalidate acknowledgement.
6. Acknowledge the whole-set/new-purchases-only warnings and confirm publication in a separate dialog. POST the exact reviewed digest, revision and shared approval phrase. No automatic publication, monetary collection, credit grant or entitlement transition occurs.
7. Inspect verified command receipts separately from current records. A failed follow-up read does not erase a valid command receipt or turn it into an unknown original command. Conversely, an invalid/lost command response never becomes a success. Explicit refresh verifies current lifecycle.
8. History loads up to the backend's 100 recent versions and 20 drafts, with full detail on selection. This is not represented as complete audit history or actor-level audit evidence. Stop Future Sales accepts a verified published offer, or the existing D6 exception for a retired offer with a server-reported live checkout. A saved draft may be explicitly discarded; history remains.

## Unsaved edits, identity and retry safety

Changing payment selection preserves **all** fields in the whole local set, so no per-option save or implicit discard is needed. Replacing the set or explicitly reloading a dirty editor requires Save Local Draft / Discard Changes / Continue Editing. Local snapshots preserve incomplete fields and remain accessible in this tab; they never become backend records. Existing local snapshots survive discarding subsequent unsaved edits. Stale snapshots cannot be published or silently rebased onto newer server terms.

Commands freeze the normalized body, target, original identity and UUID key. Synchronous instance-level exclusion blocks double submissions. Fresh identity, independent billing read and HQ role are rechecked before every command, including explicit retries; the command itself independently checks live backend authority. A changed account must return to the original identity before recovering its request. Identity values and bodies/keys remain memory-only and are not rendered, put in URLs, stored in browser storage or sent to telemetry.

Unknown outcomes retain the exact request. Only an explicit Retry Exact Request can resend it. Exact replay must bypass client preflight revision checks, since the original may already have advanced the lifecycle; backend idempotency still verifies authority and the unchanged request. No new key is silently allocated to retry changed data. Discarding recovery is disabled in flight and requires a separate warning after settlement: abandoning cannot reverse a server action. It refreshes current records before another command.

Window blur and hidden-document events immediately conceal loaded pricing information. Empty views are not needlessly concealed. Restoration is explicit, server-backed and fail-closed for session expiration, changed identity or revoked permission. Read epochs invalidate stale reads; **command instance lifetime independently governs settlement** so focus loss cannot leave a settled command locked. No grace period, timeout-based unlock or automatic retry exists. A real network timeout is an unknown outcome with its key retained.

Reload, leaving the route, account navigation, full document destruction or component destruction loses memory-only notes/retries. A beforeunload warning covers document navigation; it does not promise durable recovery or interception of every App Router navigation/browser-back case. Reinspect backend records before any new command after losing a request. No sensitive persistence is added.
