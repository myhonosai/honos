# Render deployment (Blueprint)

Status: **configuration only. Nothing has been deployed and no Render or Supabase account was changed.**
Owner hosting decision (2026-11-09): Render for the web app and API, Supabase Pro for PostgreSQL.

`render.yaml` at the repository root is a Render Blueprint. It is guarded by
`apps/api/test/render-blueprint.test.cjs`, which also runs the Blueprint's values through the real API
startup gate and the shared OIDC/session validation.

## What the Blueprint creates

| Service | Type | Public? | Build | Start | Health |
|---|---|---|---|---|---|
| `hon-web` | web | yes (only entry point) | `pnpm --filter @hon/web build` | `next start` on `PORT=3000` | `GET /api/identity/readiness` |
| `hon-api` | private service | no; reached by `hon-web` over Render's private network | `pnpm --filter @hon/api build` | `node dist/main.js` on `3001` | process exits before listening on bad config (no HTTP health check: Render supports those for web services only) |

Both: region `virginia` (Supabase project is `us-east-1`), Node `22.23.4` (same pin as CI, verified at
build start by `.github/scripts/verify-node-runtime.mjs`), pnpm `10.18.0` via corepack, dev dependencies
installed for the build even though `NODE_ENV=production`.

Deliberately **absent**:

- commit-triggered deploys (`autoDeployTrigger: off`) and preview environments (`previews.generation: off`);
- `preDeployCommand`: migrations are a separate, owner-approved step using the migration role
  (`DATABASE_URL`), which the API refuses to hold (`MIGRATION_CREDENTIAL_IN_API_PROCESS`);
- `DATABASE_URL`, `OPENROUTER_*`, `STRIPE_*`, `ZERNIO_*`, `MANUS_*`: live money, paid AI, messaging and the
  development sign-in adapter stay off.

`HON_DEPLOYMENT_ENVIRONMENT` is fixed to `staging` in Git. Promoting to `production` is a reviewed PR that
changes both services.

## Before you click Apply

`autoDeployTrigger: off` only stops deploys triggered by new commits. Render still starts deploys in two
other ways (per Render's Blueprint docs; recheck before applying):

1. **Applying (creating) the Blueprint deploys both services from `main` at once.** Apply only when the
   target database is migrated to the release, `hon_runtime` exists, the CA and every `sync: false`
   value are ready to enter during creation, and David has approved this deploy. Without them `hon-api`
   refuses to start (safe, but it is still a deploy).
2. **Blueprint Auto Sync is on by default.** A later `render.yaml` change merged to `main` (for example
   moving the label to `production`) would be applied, and can redeploy, with nobody starting it.
   **Turn Auto Sync off right after creation** (Blueprint → Settings) and sync by hand after each
   reviewed `render.yaml` change.

`HON_API_BASE_URL` is read by `apps/web/next.config.ts` `rewrites()` at **build** time: enter it before
the first `hon-web` build, and rebuild (not just restart) after changing it. The internal `hon-api`
address is only shown after creation, so expect to set it then and run one manual `hon-web` deploy.

## Values entered in the Render dashboard (`sync: false`)

| Variable | Service | Value |
|---|---|---|
| `HON_RUNTIME_DATABASE_URL` | api | Supabase **Session Pooler** URL for `hon_runtime.<project-ref>` (port 5432). No `sslmode` parameter. Never the `postgres` role. |
| `HON_DATABASE_CA_CERT` | api | PEM text of the project CA (`prod-ca-2021.crt`) |
| `HON_PUBLIC_ORIGIN` | api, web | `https://<public web host>` (origin only, same on both) |
| `HON_API_BASE_URL` | web | `http://<hon-api internal host>:3001` from the hon-api "Connect" panel |
| `HON_OIDC_ISSUER`, `_AUTHORIZATION_ENDPOINT`, `_TOKEN_ENDPOINT`, `_JWKS_URI`, `_CLIENT_ID`, `_CLIENT_SECRET` | web | from the chosen OIDC sign-in provider |
| `HON_OIDC_REDIRECT_URI` | web | exactly `<HON_PUBLIC_ORIGIN>/auth/callback` |

`HON_SESSION_JWT_SECRET` is generated by Render in the `hon-session` env group and shared by both
services. Rotating it signs everyone out.

Related: `DATABASE_TLS_AND_CONNECTIONS.md` (TLS, pooler sizing, startup codes),
`BACKUP_RESTORE_AND_RECOVERY.md` (migrations, rollback, restore), `MONITORING_AND_ALERTING.md`.

## Applying migrations: the "Database migrate (manual)" button

Migrations never run from Render. They run from `.github/workflows/database-migrate.yml`, which only
runs when someone presses **Actions → Database migrate (manual) → Run workflow** on `main`.

One-time setup (GitHub → repository **Settings → Environments**):

1. Create environment `staging`. On its page, **before adding any secret**:
   - **Deployment branches and tags** → *Selected branches and tags* → add rule `main` (only `main`).
     Without this, a workflow on any pushed branch could ask for this environment and read its secrets.
   - **Required reviewers** → add yourself, so every run waits for your approval.
2. Then add two **environment secrets**:
   - `DATABASE_URL`: the Supabase **Session pooler** string for the `postgres` role
     (`postgresql://postgres.<ref>:<db password>@aws-0-us-east-1.pooler.supabase.com:5432/postgres`),
     without any `?sslmode=...`.
   - `HON_DATABASE_CA_CERT`: full PEM text of the project CA.
3. Later, create `production` the same way, with the same branch rule and required reviewer.

Use: choose the target, then `status` (read-only), `migrate` (type the target name again in
*confirm*), or `verify` (read-only security verifier, after `infra/postgres/010` has been run).
A migrate run checks the migration checksums, prints status, applies pending files, and fails unless
the database is current afterwards. Take an off-site dump or confirm a fresh Supabase backup first.
