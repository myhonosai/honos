# Monitoring, error reporting and alerting

Status: **minimal foundation implemented in source; no log drain, alerting or vendor is configured.** Cost: $0 in code. It writes JSON to stdout/stderr for the hosting platform's built-in log collection. No paid SDK was added.

## What is captured

| Signal | Where | Event |
|---|---|---|
| Unexpected API exceptions (500) | `apps/api/src/observability/http-telemetry.ts` `HonExceptionFilter` | `http.unexpected_error` |
| API 5xx problem responses (for example 503 `PERSISTENCE_NOT_CONFIGURED`) | same | `http.server_error` |
| Malformed or oversized request bodies | `transportErrorHandler` | `http.request_rejected` (warn) |
| Database idle-connection failures | runtime pool `'error'` listener | `database.idle_client_error` |
| Invalid database configuration (once per process) | `runtime-database.service.ts` | `database.configuration_invalid` |
| Startup refusal by the production gate | `main.ts` | `startup.configuration_refused` (fatal) |
| Process crashes (`uncaughtException`, `unhandledRejection`) | `installProcessTelemetry` | `process.*` (fatal), then exit 1 so the platform restarts the process |
| Nest framework logs | `HonTelemetryLogger` | `framework.log` (route-mapping noise suppressed in production) |
| Web server rendering / route-handler errors | `apps/web/src/instrumentation.ts` (`onRequestError`) | `web.request_error` |
| Browser errors in the root error boundary | `apps/web/src/app/global-error.tsx` → `POST /api/client-errors` | `web.client_error` |

Critical-operation failures are 5xx responses on `POST/PUT/PATCH/DELETE` and are tagged `"operation":"mutation"`.

## Diagnostic identifiers

- Every API response carries `X-HON-Diagnostic-Id: hon-<uuid>`. It is generated by the server, never taken from the client, and is safe to show to a customer.
- Generic 500 bodies include it: `{"statusCode":500,"message":"Internal server error","diagnosticId":"hon-…"}`. Existing 4xx/5xx problem bodies are unchanged.
- The web global error page shows the Next.js digest as a "Support reference". The same digest appears in the `web.request_error` server log.

## Redaction (privacy and secrets)

`packages/config/src/telemetry-redaction.ts` is shared by the API and the web app. Telemetry is allowlist-first.

- Only fixed fields are emitted: `ts, level, service, event, diagnosticId, method, route, status, durationMs, operation, component, origin, errorName, sqlState, problemCode, message, stack, context, count`. Anything else a caller passes is dropped.
- Routes are logged as the matched template (`/v1/leads/:leadId/close`). Query strings are always dropped. Path segments that are not route words or UUIDs become `:value`.
- **Exception messages are never logged** (API error summaries, Nest warn/error logs, the Next.js `onRequestError` hook). Free text can carry student, family or medical details that no pattern list reliably removes. Records keep the diagnostic id, the error class name, SQLSTATE, HON problem code and well-formed stack frames. The web digest correlates a record with the user's support reference. Only Nest's own fixed lifecycle messages (`NestFactory`, `NestApplication`) are logged as text.
- PostgreSQL errors keep only the SQLSTATE. `detail`, `where`, parameters and query text are never read.
- Remaining text fields (paths, framework templates, fixed startup codes) are also scrubbed of emails, phone numbers, card-like numbers, JWTs, bearer/basic credentials, cookies, `key=value` secrets, Stripe/OpenRouter/GitHub/AWS keys, webhook secrets, connection strings, PEM blocks and long opaque tokens. Property names such as email, phone, name, student, parent, guardian, family, note, card, bank, password, token, session and cookie are always dropped.
- Browsers may send only `{kind, name, digest, path}`, same-origin, ≤ 2 KiB counted in bytes while the body streams in (the upload is cancelled at the limit, whatever `Content-Length` says). The error message and stack are never accepted from the browser. `Sec-Fetch-Site` only stops browsers; the byte limit and rate limit are what bound non-browser clients.
- Tests: `apps/api/test/observability.test.cjs` and `apps/web/test/web-error-reporting.test.ts` assert that synthetic emails, phone numbers, cards, JWTs, Stripe/OpenRouter keys, DB URLs, cookies, student names and unquoted medical details never appear in output.

- **Limit (not changed by this PR):** Next.js itself still prints uncaught server errors, including their message, to stderr outside this telemetry. Treat raw platform logs as sensitive: restrict who can read them and keep retention short until that output is reviewed.

## Cost controls

- Identical failures (same event, route, status and error identity) are emitted at most 20 times per minute per process. A `telemetry.suppressed` record carries the dropped count.
- No access logs for successful requests. 4xx responses are not logged, except body-parser rejections.
- Browser reports are capped at 120 per minute per web process.
- Recommended retention: 14–30 days on the platform's included tier.

## Health checks (configure on the hosting platform)

| Check | Endpoint | Expect | Use |
|---|---|---|---|
| API liveness | `GET /v1/health` | 200 | restart if it fails 3× in a row |
| API readiness | `GET /v1/health/ready` | 200 (503 when the DB is unreachable, misconfigured or the role is unsafe) | gate traffic and deploys |
| Web | `GET /` | 200 | uptime |
| External uptime probe | public web URL | 200 every 1–5 min | free tier of any uptime monitor (owner choice) |

## Alerting requirements (owner configures; none exist yet)

| Alert | Condition | Severity |
|---|---|---|
| API not ready | readiness non-200 for 2 min | SEV1 page |
| Crash loop | any `process.uncaught_exception` / `process.unhandled_rejection`, or more than 3 restarts in 10 min | SEV1 |
| Startup refused | any `startup.configuration_refused` | SEV1 (deploy blocked) |
| Error spike | more than 10 `http.unexpected_error` in 5 min | SEV2 |
| Mutation failures | any `http.unexpected_error` with `operation=mutation` on payment, billing or enrollment routes | SEV2 |
| Database connectivity | `database.idle_client_error` more than 5 in 5 min, or any `database.configuration_invalid` | SEV2 |
| Web errors | more than 20 `web.request_error` or `web.client_error` in 10 min | SEV3 |

## Optional external error tracker (needs owner approval)

If platform log alerts are not enough, a hosted tracker (for example a free-tier Sentry plan) can be added later behind the same redaction functions. It is **not** included: it is a new external data processor and possibly a cost. Decide data residency and enable "do not send PII" first.

## Not covered yet

- Request rate limiting across the API (only public forms, kiosk and browser reports have limits).
- Metrics or dashboards (latency percentiles, pool saturation).
- Wiring of page-level `error.tsx` boundaries to `reportClientError`. That is frontend (Codex) follow-up work. The root `global-error.tsx` is wired.
- Diagnostic-id propagation into domain command `requestId`/`correlationId`, which stay generated per command as before.
